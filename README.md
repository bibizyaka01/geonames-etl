# GeoNames ETL на Apache Airflow

Курсовая работа по предмету «Управление конфигурацией программного обеспечения».

Автор: Андреев Владимир Борисович.

## Назначение

Локальная платформа загрузки открытых географических данных GeoNames в PostgreSQL.
Основной акцент проекта — воспроизводимое развёртывание через Docker Compose,
конфигурация вне кода и автоматические проверки в GitHub Actions.

## Планируемая архитектура

- Apache Airflow 3 с Python 3.12 и CeleryExecutor: API server, scheduler,
  DAG processor, triggerer и масштабируемые workers.
- Redis как брокер задач.
- PostgreSQL 16: отдельные экземпляры для метаданных Airflow и DWH.
- Одноразовый init-контейнер для первоначальной настройки Airflow.
- Слои DWH: `stg`, `core`, `mart`.
- Три DAG: справочники, первичная загрузка и ежедневные изменения.
- Режим `lite` для разработки и `full` для полного набора данных.

Начальная конфигурация предусматривает одного worker. Масштабирование до трёх
workers проверяется после отладки загрузки.

## Структура

```text
dags/                  DAG Airflow
src/                   общий Python-код ETL
sql/init/              схемы и таблицы DWH
sql/transformations/   преобразования данных
docker/                скрипты настройки контейнеров
tests/                 проверки поведения ETL
```

## Непрерывная интеграция

`.github/workflows/ci.yml` запускается на каждый push, pull request и вручную
через вкладку Actions → CI → Run workflow. Все задания выполняются на
GitHub-hosted Ubuntu runner, поэтому Docker Desktop на компьютере автора
для CI запускать не требуется.

Порядок проверок:

1. Ruff 0.17.5 проверяет Python-код по `pyproject.toml`: базовые ошибки,
   неопределённые имена и порядок импортов.
2. После успеха линтера собирается образ `geonames-airflow:ci` из Dockerfile.
3. В собранном образе выполняются `python -m pip check`, импорт и валидация
   ровно трёх ожидаемых DAG через `docker/check-dags.py` и тесты парсеров.

Проверочные контейнеры имеют лимит 512 МиБ RAM и 1 CPU, сеть отключена.
Настройки `.env`, пароли и GitHub Secrets для этих проверок не нужны.
Реальные архивы GeoNames в CI не скачиваются. Интеграционные тесты DWH
пропускаются без подключения к БД: это не проверка ETL на реальном хранилище.
Права workflow ограничены чтением репозитория, Docker-образ не публикуется.
Новый запуск той же ветки отменяет незавершённый старый запуск CI.

Проверка DAG локально после сборки:

```powershell
docker build -t geonames-airflow:ci .
docker run --rm --network none --memory 512m --cpus 1 --entrypoint python geonames-airflow:ci /opt/airflow/docker/check-dags.py
docker run --rm --network none --memory 512m --cpus 1 --entrypoint python geonames-airflow:ci -m pip check
```

## Запуск платформы

Требуются Docker с Linux-контейнерами и Docker Compose v2. Команды выполняются
из корня репозитория. На Windows сначала запустите Docker Desktop.

Подготовьте локальные настройки в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File docker/setup-env.ps1
```

Скрипт создаёт `.env` из шаблона и генерирует пароли и ключи. При повторном
запуске существующие непустые значения сохраняются. Секреты не выводятся в консоль.
Откройте `.env` в редакторе, чтобы посмотреть пароль администратора.

Запустите платформу одной командой:

```powershell
docker compose up -d --build
```

Compose дожидается готовности PostgreSQL и Redis, затем init-контейнер выполняет
миграции Airflow и создаёт пользователя, если его ещё нет. После этого стартуют
компоненты Airflow. Worker дополнительно ждёт готовности API server.
Первый запуск включает скачивание образов и может занять несколько минут.

- Airflow: http://localhost:8080, пользователь `AIRFLOW_ADMIN_USERNAME`
  (по умолчанию `admin`), пароль `AIRFLOW_ADMIN_PASSWORD` из `.env`.
- DWH для DBeaver: хост `localhost`, порт `5433`, база `geonames`, пользователь
  `geonames`, пароль `DWH_PASSWORD` из `.env` (если настройки не менялись).
- Служебная БД и Redis не публикуют порты на хост.

Проверка состояния и диагностика:

```powershell
docker compose ps -a
docker compose logs --tail 100 airflow-init
docker compose logs --tail 100 airflow-apiserver airflow-worker
```

Нормальное состояние: семь сервисов работают и имеют статус `healthy`,
`airflow-init` завершён с кодом `0`. В UI доступен DAG `geonames_references`.
Также доступен DAG `geonames_initial` для ручной первичной загрузки.

По умолчанию работает облегчённая конфигурация с CeleryExecutor без triggerer:
текущий DAG не использует отложенные (deferrable) задачи. Для полной архитектуры:

```powershell
docker compose --profile full up -d
```

Профиль `full` добавляет triggerer. Если он уже работает, отключение профиля
само по себе не остановит его: используйте `docker compose stop airflow-triggerer`.
CLI-проверки worker, DAG processor и triggerer выполняются раз в 120 секунд
вместо 30. Это уменьшает частоту запуска Python-процессов, но замедляет обнаружение
отказов. Повторный разбор DAG также выполняется с интервалом 120 секунд,
поэтому изменения кода могут появляться с задержкой.

Остановить платформу с сохранением БД, логов и скачанных файлов:

```powershell
docker compose down
```

Не добавляйте `--volumes`, если нужно сохранить данные.
Образы PostgreSQL закреплены на основной версии 16, Redis — на ветке 7.2;
эти теги допускают обновления исправлений от издателя.

## Данные и конфигурация контейнеров

Именованные тома сохраняют две БД, общие логи Airflow и файлы GeoNames.
Код DAG, Python и SQL включён в образ; после его изменения повторите
`docker compose up -d --build`.

Все сервисы подключены к сети `platform` типа bridge. Внешние подключения
доступны только через `127.0.0.1:8080` и `127.0.0.1:5433`; исходящий HTTPS
из контейнеров разрешён для скачивания GeoNames.

Подключение к DWH передаётся через `AIRFLOW_CONN_GEONAMES_DWH` и будет
использоваться в DAG как connection ID `geonames_dwh`.
Настройки PostgreSQL в `.env` допускают ASCII-буквы, цифры, `_` и `-`, поскольку
они включаются в URI подключения. Сгенерированные пароли соответствуют этому формату.

Изменение пароля PostgreSQL в `.env` не меняет пароль в уже созданной базе.
Аналогично init не меняет пароль существующего администратора Airflow.
Ключи Fernet, JWT и API должны оставаться одинаковыми для всех компонентов
и сохраняться при пересоздании контейнеров.

SQL из `sql/init` выполняется PostgreSQL только при создании пустого тома DWH.
Изменение этих файлов не применяет миграции к существующей базе автоматически.

Сначала используется один worker с одним процессом исполнения задач.
Масштабирование до трёх workers и распределение задач проверены.

### Демонстрация трёх воркеров

Увеличение числа контейнеров само по себе не повышает параллелизм задач.
Для демонстрации одновременно задаются число workers и общий параллелизм.
Задачи справочников независимы, поэтому могут выполняться одновременно:

```powershell
$env:GEONAMES_TASK_PARALLELISM = '3'
$env:GEONAMES_CELERY_POOL = 'solo'
docker compose up -d --scale airflow-worker=3 --wait --wait-timeout 300
```

После готовности всех воркеров запустите `geonames_references` в UI.
При проверке использовался pool `solo`, concurrency каждого worker — 1,
prefetch multiplier — 1. Выбор solo не гарантирует меньшего расхода памяти.
Во время длинной задачи solo может задерживать ответ на Celery inspect ping;
для обычной работы применяется `prefork`.

По окончании задач верните экономную конфигурацию:

```powershell
$env:GEONAMES_TASK_PARALLELISM = '1'
$env:GEONAMES_CELERY_POOL = 'prefork'
docker compose up -d --scale airflow-worker=1 --wait --wait-timeout 300
```

Эти переменные задаются для текущего PowerShell-процесса и имеют приоритет
над `.env`; сам файл `.env` команды не меняют. По умолчанию параллелизм 1,
pool prefork, concurrency 1. Число процессов синхронизации CeleryExecutor — 1.
С тремя workers индивидуальные лимиты суммарно превышают бюджет WSL:
проверяйте фактическое потребление и не совмещайте демонстрацию с full-загрузкой.

## Ограничение ресурсов на Windows

Первый запуск без ограничений привёл к высокой загрузке памяти хоста.
В Compose заданы жёсткие лимиты памяти и CPU; это начальные бюджеты,
которые проверены при загрузке справочников; полный набор GeoNames ещё не проверен.

| Сервис | Лимит памяти |
| --- | ---: |
| API server | 1024 МиБ |
| Scheduler | 768 МиБ |
| DAG processor | 768 МиБ |
| Triggerer | 512 МиБ |
| Worker | 1024 МиБ |
| PostgreSQL metadata | 256 МиБ |
| PostgreSQL DWH | 384 МиБ |
| Redis | 128 МиБ |
| Init (завершается до запуска Airflow) | 768 МиБ |

Сумма лимитов семи постоянно работающих контейнеров — 4,25 ГиБ;
с triggerer в профиле `full` — 4,75 ГиБ.
Это пределы отдельных контейнеров, а не резервирование памяти. Общий лимит WSL
ниже их суммы, поэтому фактическое потребление при ETL нужно измерять:
одновременное достижение всех лимитов приведёт к нехватке памяти внутри WSL.
Это не лимит всей виртуальной машины WSL: Linux, Docker, кеш и сборка образов
также потребляют память. `memswap_limit`, равный `mem_limit`, отключает swap
для соответствующего контейнера. При превышении лимита процесс может быть
завершён OOM; автоматически повышать лимиты до измерений не следует.
Для компонентов Airflow временно отключён автоматический перезапуск,
чтобы сбои не превращались в непрерывный цикл запуска.

Для компьютера с 16 ГБ RAM подготовлен `docker/wslconfig.example`:
4 ГБ RAM и 4 логических CPU на WSL, 2 ГБ swap. Swap использует диск и может
замедлять работу; он не заменяет оперативную память. Настройки действуют
на все WSL2-дистрибутивы. Перенесите секцию в `%USERPROFILE%\.wslconfig`,
сохранив другие настройки, если файл уже существует.
Затем выйдите из Docker Desktop, выполните `wsl --shutdown` (останавливает все
WSL-дистрибутивы) и запустите Docker Desktop заново.
В секции `[experimental]` включён `autoMemoryReclaim=gradual` для постепенного
возврата кешированной памяти Windows. Это не освобождает память работающих
процессов и не гарантирует мгновенного уменьшения Vmmem.

После применения общего лимита проверяйте запуск поэтапно:

```powershell
docker compose up -d postgres-meta postgres-dwh redis
docker stats --no-stream
docker compose up airflow-init
docker compose up -d airflow-apiserver
docker stats --no-stream
docker compose up -d airflow-scheduler airflow-dag-processor
docker stats --no-stream
docker compose up -d airflow-worker
docker compose ps -a
docker stats --no-stream
```

Если образ изменён, предварительно соберите его: `docker compose build airflow-init`.
При выходе контейнера проверьте OOMKilled (пример для worker):

```powershell
docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' geonames-etl-airflow-worker-1
docker compose logs --tail 50 airflow-worker
```

Лимиты не гарантируют успешный запуск Airflow. Если сервису не хватает памяти,
скорректируйте его бюджет после измерения либо запускайте только нужные для
текущего этапа компоненты. Full с одним worker и отдельно три workers
проверены; совмещать эти нагрузки на текущем компьютере не следует.

## Образ Airflow

Базовый образ: `apache/airflow:3.4.0-python3.12`. Один образ будет использоваться
всеми компонентами Airflow. Дополнительные зависимости устанавливаются при сборке
от пользователя `airflow`; установка пакетов при запуске не требуется.

В `requirements.txt` зафиксированы зависимости для CeleryExecutor, PostgreSQL,
HTTP-запросов и FAB auth manager (вход по логину и паролю).
Для потокового COPY используется Psycopg 3.

В `docker/constraints-3.12.txt` сохранён официальный список совместимых версий:
https://raw.githubusercontent.com/apache/airflow/constraints-3.4.0/constraints-3.12.txt

Constraints ограничивают версии зависимостей, но не устанавливают все перечисленные
пакеты. При обновлении Airflow нужно согласованно обновлять базовый образ,
версию Airflow в команде pip, requirements и constraints.

Сборка из каталога проекта:

```powershell
docker build -t geonames-airflow:dev .
```

Проверка образа без запуска платформы:

```powershell
docker run --rm geonames-airflow:dev python --version
docker run --rm geonames-airflow:dev version
docker run --rm geonames-airflow:dev pip check
```

В образ копируются DAG, общий Python-код и SQL. `.dockerignore` ограничивает
контекст сборки необходимыми файлами, исключая `.env` и каталог `.git`.

## Данные

### Ежедневные изменения и удаления

DAG `geonames_delta` по умолчанию создаётся на паузе. Расписание — 08:00 UTC
ежедневно, без автоматического catchup Airflow. Целевая дата изменений —
`data_interval_end` в UTC минус один день: запуск 21 ноября обрабатывает
файлы по 20 ноября включительно. Для ручного запуска задайте конечную дату
в параметре `change_date` (`YYYY-MM-DD`). Дата в имени файла относится к
дню изменений: например, файл за 20 ноября опубликован 21 ноября.

Загрузчик сам проходит все даты после сохранённой отметки до целевой включительно.
Каждый день коммитится отдельно. После сбоя повторная попытка продолжает
с последнего успешно обработанного дня; при отсутствии новых дней файлы
не скачиваются. Поэтому `catchup=False` не приводит к пропуску данных:
восстановление выполняется кодом задачи по отметке DWH.

Это возможно только при наличии всех необходимых файлов. В каталоге GeoNames
не гарантируется доступность истории за весь период простоя. Если нужный файл
вернул 404, обработка останавливается, дата не перепрыгивается. Нужен архив
отсутствующих дельт либо повторная initial из свежего снимка. Автоматическая
полная перезагрузка при 404 не выполняется.

`sql/init/004-delta.sql` добавляет staging-таблицы дельты и `last_delta_date`
в `core.dataset_state`. На существующей базе файл применяется явно:

```powershell
Get-Content -Raw -Encoding UTF8 sql/init/004-delta.sql | docker compose exec -T postgres-dwh psql -v ON_ERROR_STOP=1 -U geonames -d geonames
```

Начальная граница — `snapshot_date`: дата изменения исходного архива из
HTTP Last-Modified, переведённая в `Europe/Berlin` (GeoNames указывает
Central European Time в каталоге выгрузок). Полный timestamp сохраняется в
`source_last_modified`. `loaded_at` отражает только время нашей загрузки и
больше не используется для выбора первой дельты. Дневной архив от 17 ноября
считается покрывающим изменения по 16 ноября; первой требуется дельта с именем
за 17 ноября, публикуемая 18-го. При отсутствии last_delta_date используется
snapshot_date минус один день. Это допущение дневного цикла источника, а не
предоставленная GeoNames транзакционная метка.

Миграция `sql/init/005-source-snapshot.sql` добавляет эти поля. На существующей
БД примените её так же, как 004, а затем повторите initial. Старым записям дата
источника не приписывается автоматически. При неизвестной дате снимка дельта
отказывается менять данные; initial без корректного Last-Modified также
завершается ошибкой. Повторная initial атомарно обновляет метаданные источника
вместе с core и сбрасывает last_delta_date.

Last-Modified — метаданные файла, а не официальная метка транзакционного снимка
GeoNames. Это устраняет зависимость от наших часов загрузки, но не доказывает
атомарную согласованность снимка с выгрузками изменений на стороне источника.
Не включайте DAG до initial.

В режиме `full` выполняются upsert всех изменений и удаления по geonameid.
В режиме `lite` обновляются и удаляются только уже загруженные объекты;
новые идентификаторы не добавляются. Это синхронизация фиксированной выборки,
а не точное ежедневное воспроизведение состава cities15000. Для обновления
состава lite повторите initial; он также сбрасывает отметку последней дельты.
Режим воркера должен совпадать с режимом в dataset_state.

Оба файла загружаются до изменения данных; HTTP 404 приводит к ошибке и повтору,
а опубликованный пустой файл допустим. Предел — 256 МиБ на файл; строки
проверяются на количество полей. Одна транзакция выполняет COPY в staging,
upsert, удаления и обновление отметки дня. Удаление имеет приоритет, если ID
присутствует в обоих файлах. Advisory lock общий с initial.
Повторная или более старая дата не изменяет данные; пропуск дня отвергается.
Временные файлы удаляются при обычном завершении, включая ошибку; аварийный
выход процесса может оставить каталог. В XCom возвращается только статистика.

Запуск интеграционных тестов (требуется DWH и собранный образ):

```powershell
Get-Content -Raw -Encoding UTF8 tests/test_delta_db.py | docker compose run -T --rm --no-deps --entrypoint python airflow-worker -
```

### Первичная загрузка GeoNames

`sql/init/003-geoname.sql` создаёт `stg.geoname` (19 текстовых столбцов),
типизированную `core.geoname` с ключом `geonameid`, индексом страны/типа и
`core.dataset_state` для режима, числа строк и времени последней первичной загрузки.
Витрины `mart.cities_by_country` и `mart.object_counts` вычисляются при запросе.
На уже созданной БД примените SQL явно:

```powershell
Get-Content -Raw -Encoding UTF8 sql/init/003-geoname.sql | docker compose exec -T postgres-dwh psql -v ON_ERROR_STOP=1 -U geonames -d geonames
```

DAG `geonames_initial` не имеет расписания и запускается вручную в UI после
загрузки справочников. `GEONAMES_MODE=lite` выбирает `cities15000.zip`,
`GEONAMES_MODE=full` — `allCountries.zip`. Смена режима требует пересоздания
компонентов Airflow для применения окружения. Полный режим проверен
17.11.2026: 13 484 091 объект, DAG завершился успешно за 219,4 секунды.
Повторный запуск сверяет полный снимок с core.geoname: добавляет новые ID,
обновляет только отличающиеся строки и удаляет ID, отсутствующие в снимке.
Неизменившиеся строки не перезаписываются, TRUNCATE core.geoname не выполняется.
Дата modification_date не используется как единственный фильтр: изменения
в пределах дня, исправления и удаления обнаруживаются сравнением со снимком.
Устаревший снимок относительно source_last_modified или last_delta_date
отвергается. При смене full на lite состав core станет соответствовать lite,
поэтому остальные объекты будут удалены; режим выбирайте осознанно.

Архив скачивается блоками 64 КиБ в `/opt/airflow/data/initial`, внутри общего
тома. Распаковка выполняется потоком из ZIP прямо в PostgreSQL COPY, без отдельного
распакованного файла и без загрузки архива целиком в память. Обрабатывается
одна строка за раз. Ограничения: архив 2 ГиБ, распакованный файл 20 ГиБ,
строка 1 МиБ; предусмотрены сетевые таймауты и таймаут задачи 12 часов.
Режим full может требовать существенного места в томе DWH для staging,
core, индексов и WAL, даже при небольшом расходе памяти Python.

Staging, сверка core и состояние набора фиксируются одной транзакцией.
После COPY создаётся временная типизированная таблица полного снимка с первичным
ключом и статистикой. Она требует дополнительного места на диске и удаляется
при commit. Пустой или некорректный снимок не должен приводить к удалению core.
Пустой файл, неправильное число полей, ошибка типов или ключей откатывают
изменения. Транзакция берёт advisory lock `geonames.geoname`; ежедневная дельта
должна использовать тот же ключ. После успешного commit архив удаляется.
При ошибке ZIP или `.zip.part` сохраняется для диагностики; очередная попытка
перезаписывает файл своего режима. Архивы разных режимов очищаются независимо.
Сами таблицы staging остаются на диске до следующей загрузки.

Примеры запросов из DBeaver:

```sql
SELECT * FROM core.dataset_state;
SELECT country_name, name, population
FROM mart.cities_by_country
ORDER BY population DESC NULLS LAST LIMIT 10;
SELECT * FROM mart.object_counts ORDER BY object_count DESC;
```

После испытания полный набор оставлен в основной DWH, локальный `.env`
переключён на `GEONAMES_MODE=full`. Шаблон `.env.example` по-прежнему начинает
с lite. Смена переменной сама по себе не меняет данные: новый initial сверяет
core.geoname с выбранным снимком. В рабочем экземпляре дельта включена:
ежедневно в 08:00 UTC (11:00 Europe/Moscow). Docker должен работать;
после простоя восстановление зависит от доступности всех пропущенных файлов.

При длительной загрузке код пишет прогресс скачивания каждые 64 МиБ и
COPY каждые 500 000 строк. Дополнительно прогресс можно смотреть в
`pg_stat_progress_copy`; после COPY идёт SQL-преобразование, в этой view его уже нет.

Интеграционные тесты отката после загрузки lite выполняются внутри worker:

```powershell
docker compose run -T --rm --no-deps --env SNAPSHOT_TEST_DATABASE=geonames_snapshot_tests_20261121 --volume "${PWD}/tests:/checks:ro" --entrypoint python airflow-worker -m unittest discover -s /checks -p test_initial_db.py
```

Эти тесты и `test_snapshot_sync_db.py` требуют заранее подготовленной отдельной
БД с именем `geonames_snapshot_tests_*`, схемами проекта и минимальными
справочниками. Они не предназначены для выполнения против основной DWH.
Режим сверки проверен на изолированных наборах, включая неизменность физических
версий одинаковых строк. Сверка полного набора проверена на существующей DWH:
добавлены 272 объекта, обновлены 26 566, удалены 16; в результате 13 484 347 строк.
У контрольных неизменившихся объектов сохранились xmin и ctid.
Временные структуры сверки увеличивали размер файлов БД примерно до 9,6 ГБ;
после завершения размер DWH вернулся примерно к 5 ГБ. VHDX Docker при этом
не обязан автоматически уменьшаться на физическом диске.

### Таблицы справочников

`sql/init/002-reference-tables.sql` создаёт четыре пары таблиц:
`stg.country` / `core.country`, `stg.admin1` / `core.admin1`,
`stg.feature_code` / `core.feature_code`, `stg.timezone` / `core.timezone`.
Staging сохраняет порядок столбцов исходных файлов и текстовые значения.
Core использует числовые типы для населения, площади, идентификаторов и смещений
часовых поясов; коды остаются текстом, чтобы сохранялись ведущие нули.
Ключи: код страны, полный код региона, полный код типа объекта и пара
`(country_code, timezone_id)` соответственно. Внешние ключи пока не вводятся:
сначала нужно проверить полноту связей реальных справочников.
Загрузка реализована DAG `geonames_references` (изначально приостановлен).

### DAG справочников

Файл: `dags/geonames_references.py`, общий код: `src/geonames_etl/references.py`.
Четыре задачи независимы и по умолчанию выполняются по одной: страны, регионы, типы объектов,
часовые пояса. Расписание — ежедневно в UTC, без обработки старых периодов.
Предусмотрены два повтора с интервалом 30 секунд и таймаут задачи 10 минут.

Каждая задача скачивает соответствующий TSV в уникальный временный каталог
тома `geonames-data`, загружает строки через Psycopg COPY в `stg`, затем выполняет
SQL из `sql/transformations/reference_*.sql` для полного обновления `core`.
Staging и core обновляются в одной транзакции с проверкой числа строк;
ошибка откатывает изменения этой задачи. Четыре справочника обновляются независимо,
а не в общей транзакции DAG. Блокировка PostgreSQL сериализует обновления одного
справочника. Повторная успешная загрузка того же файла не создаёт дубликатов.

Комментарии страны и заголовок часовых поясов пропускаются. Пустые поля сохраняются
в staging, а в core преобразуются в NULL. Обратные слеши и кавычки в значениях
не интерпретируются как управляющие символы COPY. Скачивание ограничено 10 МиБ
на файл, используются блоки 64 КиБ и сетевые таймауты. Временные файлы удаляются
при завершении задачи, в том числе при обычной ошибке; аварийное завершение
процесса может оставить файлы. XCom содержит только число загруженных строк.

Подключение `geonames_dwh` разрешается через Task SDK только во время выполнения
задачи. Импорт файла DAG не обращается к сети или БД.

Проверки парсера на собранном образе из PowerShell:

```powershell
docker run --rm --memory 512m --cpus 1 --mount "type=bind,source=$((Get-Location).Path)/tests,target=/checks,readonly" --entrypoint python geonames-airflow:dev -m unittest discover -s /checks -v
```

Проверка импорта для Airflow 3.4:

```powershell
docker run --rm --memory 512m --cpus 1 --entrypoint python geonames-airflow:dev -c "from airflow.dag_processing.dagbag import DagBag; b = DagBag('/opt/airflow/dags'); assert not b.import_errors, b.import_errors; assert 'geonames_references' in b.dags; print(b.dags['geonames_references'].task_ids)"
```

После успешных проверок пересоберите и обновите компоненты Airflow с учётом
доступной памяти (по одному, как описано в разделе ресурсов), затем включите
DAG и запустите его в UI. При первом включении возможен запуск по расписанию:
перед ручным запуском проверьте, что уже нет активного запуска. После выполнения
проверьте количество строк в четырёх таблицах core.

На новой БД SQL выполняется автоматически. Для уже созданного тома примените
файл явно (значения `-U` и `-d` должны соответствовать вашему `.env`):

```powershell
Get-Content -Raw -Encoding UTF8 sql/init/002-reference-tables.sql | docker compose exec -T postgres-dwh psql -v ON_ERROR_STOP=1 -U geonames -d geonames
```

Создание выполняется в транзакции, повторный запуск сохраняет существующие
таблицы и данные. `IF NOT EXISTS` не изменяет структуру уже существующей таблицы:
для последующих изменений потребуются отдельные миграции.
