# GeoNames ETL на Apache Airflow

Курсовая работа по предмету «Управление конфигурацией программного обеспечения».

Автор: Андреев Владимир Борисович.

## Назначение

Локальная платформа загрузки открытых географических данных GeoNames в PostgreSQL.
Основной акцент проекта — воспроизводимое развёртывание через Docker Compose,
конфигурация вне кода и автоматические проверки в GitHub Actions.

## Планируемая архитектура

- Apache Airflow 3 с Python 3.12 и CeleryExecutor: API server, scheduler,
  DAG processor, triggerer и масштабируемые workers.
- Redis как брокер задач.
- PostgreSQL 16: отдельные экземпляры для метаданных Airflow и DWH.
- Одноразовый init-контейнер для первоначальной настройки Airflow.
- Слои DWH: `stg`, `core`, `mart`.
- Три DAG: справочники, первичная загрузка и ежедневные изменения.
- Режим `lite` для разработки и `full` для полного набора данных.

Начальная конфигурация предусматривает одного worker. Масштабирование до трёх
workers проверяется после отладки загрузки.

## Структура

```text
dags/                  DAG Airflow
src/                   общий Python-код ETL
sql/init/              схемы и таблицы DWH
sql/transformations/   преобразования данных
docker/                скрипты настройки контейнеров
tests/                 проверки поведения ETL
```

## Текущее состояние

Созданы образ Airflow, Docker Compose и автоматическая инициализация платформы.
При первом запуске создаются служебная БД, администратор Airflow и схемы DWH.
Добавлен DAG справочников `geonames_references`; проверены импорт и два успешных
запуска на реальных данных. Основная таблица GeoNames и CI — следующие этапы.

## Запуск платформы

Требуются Docker с Linux-контейнерами и Docker Compose v2. Команды выполняются
из корня репозитория. На Windows сначала запустите Docker Desktop.

Подготовьте локальные настройки в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File docker/setup-env.ps1
```

Скрипт создаёт `.env` из шаблона и генерирует пароли и ключи. При повторном
запуске существующие непустые значения сохраняются. Секреты не выводятся в консоль.
Откройте `.env` в редакторе, чтобы посмотреть пароль администратора.

Запустите платформу одной командой:

```powershell
docker compose up -d --build
```

Compose дожидается готовности PostgreSQL и Redis, затем init-контейнер выполняет
миграции Airflow и создаёт пользователя, если его ещё нет. После этого стартуют
компоненты Airflow. Worker дополнительно ждёт готовности API server.
Первый запуск включает скачивание образов и может занять несколько минут.

- Airflow: http://localhost:8080, пользователь `AIRFLOW_ADMIN_USERNAME`
  (по умолчанию `admin`), пароль `AIRFLOW_ADMIN_PASSWORD` из `.env`.
- DWH для DBeaver: хост `localhost`, порт `5433`, база `geonames`, пользователь
  `geonames`, пароль `DWH_PASSWORD` из `.env` (если настройки не менялись).
- Служебная БД и Redis не публикуют порты на хост.

Проверка состояния и диагностика:

```powershell
docker compose ps -a
docker compose logs --tail 100 airflow-init
docker compose logs --tail 100 airflow-apiserver airflow-worker
```

Нормальное состояние: семь сервисов работают и имеют статус `healthy`,
`airflow-init` завершён с кодом `0`. В UI доступен DAG `geonames_references`.

По умолчанию работает облегчённая конфигурация с CeleryExecutor без triggerer:
текущий DAG не использует отложенные (deferrable) задачи. Для полной архитектуры:

```powershell
docker compose --profile full up -d
```

Профиль `full` добавляет triggerer. Если он уже работает, отключение профиля
само по себе не остановит его: используйте `docker compose stop airflow-triggerer`.
CLI-проверки worker, DAG processor и triggerer выполняются раз в 120 секунд
вместо 30. Это уменьшает частоту запуска Python-процессов, но замедляет обнаружение
отказов. Повторный разбор DAG также выполняется с интервалом 120 секунд,
поэтому изменения кода могут появляться с задержкой.

Остановить платформу с сохранением БД, логов и скачанных файлов:

```powershell
docker compose down
```

Не добавляйте `--volumes`, если нужно сохранить данные.
Образы PostgreSQL закреплены на основной версии 16, Redis — на ветке 7.2;
эти теги допускают обновления исправлений от издателя.

## Данные и конфигурация контейнеров

Именованные тома сохраняют две БД, общие логи Airflow и файлы GeoNames.
Код DAG, Python и SQL включён в образ; после его изменения повторите
`docker compose up -d --build`.

Все сервисы подключены к сети `platform` типа bridge. Внешние подключения
доступны только через `127.0.0.1:8080` и `127.0.0.1:5433`; исходящий HTTPS
из контейнеров разрешён для скачивания GeoNames.

Подключение к DWH передаётся через `AIRFLOW_CONN_GEONAMES_DWH` и будет
использоваться в DAG как connection ID `geonames_dwh`.
Настройки PostgreSQL в `.env` допускают ASCII-буквы, цифры, `_` и `-`, поскольку
они включаются в URI подключения. Сгенерированные пароли соответствуют этому формату.

Изменение пароля PostgreSQL в `.env` не меняет пароль в уже созданной базе.
Аналогично init не меняет пароль существующего администратора Airflow.
Ключи Fernet, JWT и API должны оставаться одинаковыми для всех компонентов
и сохраняться при пересоздании контейнеров.

SQL из `sql/init` выполняется PostgreSQL только при создании пустого тома DWH.
Изменение этих файлов не применяет миграции к существующей базе автоматически.

Сначала используется один worker с одним процессом исполнения задач.
Проверка масштабирования до трёх workers запланирована после реализации ETL.

## Ограничение ресурсов на Windows

Первый запуск без ограничений привёл к высокой загрузке памяти хоста.
В Compose заданы жёсткие лимиты памяти и CPU; это начальные бюджеты,
которые проверены при загрузке справочников; полный набор GeoNames ещё не проверен.

| Сервис | Лимит памяти |
| --- | ---: |
| API server | 1024 МиБ |
| Scheduler | 768 МиБ |
| DAG processor | 768 МиБ |
| Triggerer | 512 МиБ |
| Worker | 1024 МиБ |
| PostgreSQL metadata | 256 МиБ |
| PostgreSQL DWH | 384 МиБ |
| Redis | 128 МиБ |
| Init (завершается до запуска Airflow) | 768 МиБ |

Сумма лимитов семи постоянно работающих контейнеров — 4,25 ГиБ;
с triggerer в профиле `full` — 4,75 ГиБ.
Это пределы отдельных контейнеров, а не резервирование памяти. Общий лимит WSL
ниже их суммы, поэтому фактическое потребление при ETL нужно измерять:
одновременное достижение всех лимитов приведёт к нехватке памяти внутри WSL.
Это не лимит всей виртуальной машины WSL: Linux, Docker, кеш и сборка образов
также потребляют память. `memswap_limit`, равный `mem_limit`, отключает swap
для соответствующего контейнера. При превышении лимита процесс может быть
завершён OOM; автоматически повышать лимиты до измерений не следует.
Для компонентов Airflow временно отключён автоматический перезапуск,
чтобы сбои не превращались в непрерывный цикл запуска.

Для компьютера с 16 ГБ RAM подготовлен `docker/wslconfig.example`:
4 ГБ RAM и 4 логических CPU на WSL, 2 ГБ swap. Swap использует диск и может
замедлять работу; он не заменяет оперативную память. Настройки действуют
на все WSL2-дистрибутивы. Перенесите секцию в `%USERPROFILE%\.wslconfig`,
сохранив другие настройки, если файл уже существует.
Затем выйдите из Docker Desktop, выполните `wsl --shutdown` (останавливает все
WSL-дистрибутивы) и запустите Docker Desktop заново.
В секции `[experimental]` включён `autoMemoryReclaim=gradual` для постепенного
возврата кешированной памяти Windows. Это не освобождает память работающих
процессов и не гарантирует мгновенного уменьшения Vmmem.

После применения общего лимита проверяйте запуск поэтапно:

```powershell
docker compose up -d postgres-meta postgres-dwh redis
docker stats --no-stream
docker compose up airflow-init
docker compose up -d airflow-apiserver
docker stats --no-stream
docker compose up -d airflow-scheduler airflow-dag-processor
docker stats --no-stream
docker compose up -d airflow-worker
docker compose ps -a
docker stats --no-stream
```

Если образ изменён, предварительно соберите его: `docker compose build airflow-init`.
При выходе контейнера проверьте OOMKilled (пример для worker):

```powershell
docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' geonames-etl-airflow-worker-1
docker compose logs --tail 50 airflow-worker
```

Лимиты не гарантируют успешный запуск Airflow. Если сервису не хватает памяти,
скорректируйте его бюджет после измерения либо запускайте только нужные для
текущего этапа компоненты. Полный режим и три workers требуют отдельной проверки.

Проверка 17.11.2026 на Windows с 16 ГБ RAM: восемь сервисов достигли `healthy`,
init завершился успешно, вход администратора через API проверен, в DWH созданы
схемы `stg`, `core`, `mart`. При одном worker и пустом списке DAG суммарное
потребление контейнеров по `docker stats` составило около 1,4 ГиБ; в Windows
оставалось около 3,5 ГиБ свободной физической памяти. Это измерение простоя,
а не оценка потребления при ETL. Общий расход WSL может быть выше показателей
`docker stats` из-за кеша и системных процессов.

## Образ Airflow

Базовый образ: `apache/airflow:3.4.0-python3.12`. Один образ будет использоваться
всеми компонентами Airflow. Дополнительные зависимости устанавливаются при сборке
от пользователя `airflow`; установка пакетов при запуске не требуется.

В `requirements.txt` зафиксированы зависимости для CeleryExecutor, PostgreSQL,
HTTP-запросов и FAB auth manager (вход по логину и паролю).
Для потокового COPY используется Psycopg 3.

В `docker/constraints-3.12.txt` сохранён официальный список совместимых версий:
https://raw.githubusercontent.com/apache/airflow/constraints-3.4.0/constraints-3.12.txt

Constraints ограничивают версии зависимостей, но не устанавливают все перечисленные
пакеты. При обновлении Airflow нужно согласованно обновлять базовый образ,
версию Airflow в команде pip, requirements и constraints.

Сборка из каталога проекта:

```powershell
docker build -t geonames-airflow:dev .
```

Проверка образа без запуска платформы:

```powershell
docker run --rm geonames-airflow:dev python --version
docker run --rm geonames-airflow:dev version
docker run --rm geonames-airflow:dev pip check
```

В образ копируются DAG, общий Python-код и SQL. `.dockerignore` ограничивает
контекст сборки необходимыми файлами, исключая `.env` и каталог `.git`.

## Настройки

Шаблон `.env.example` описывает настройки без реальных секретов.
Для подготовки используйте `docker/setup-env.ps1`, как описано выше.
Файл `.env` предназначен для локальных настроек и исключён из Git.
На других ОС можно вручную скопировать шаблон и заполнить все пароли и ключи;

## Данные

### Таблицы справочников

`sql/init/002-reference-tables.sql` создаёт четыре пары таблиц:
`stg.country` / `core.country`, `stg.admin1` / `core.admin1`,
`stg.feature_code` / `core.feature_code`, `stg.timezone` / `core.timezone`.
Staging сохраняет порядок столбцов исходных файлов и текстовые значения.
Core использует числовые типы для населения, площади, идентификаторов и смещений
часовых поясов; коды остаются текстом, чтобы сохранялись ведущие нули.
Ключи: код страны, полный код региона, полный код типа объекта и пара
`(country_code, timezone_id)` соответственно. Внешние ключи пока не вводятся:
сначала нужно проверить полноту связей реальных справочников.
Загрузка реализована DAG `geonames_references` (изначально приостановлен).

### DAG справочников

Файл: `dags/geonames_references.py`, общий код: `src/geonames_etl/references.py`.
Четыре задачи выполняются последовательно: страны, регионы, типы объектов,
часовые пояса. Расписание — ежедневно в UTC, без обработки старых периодов.
Предусмотрены два повтора с интервалом 30 секунд и таймаут задачи 10 минут.

Каждая задача скачивает соответствующий TSV в уникальный временный каталог
тома `geonames-data`, загружает строки через Psycopg COPY в `stg`, затем выполняет
SQL из `sql/transformations/reference_*.sql` для полного обновления `core`.
Staging и core обновляются в одной транзакции с проверкой числа строк;
ошибка откатывает изменения этой задачи. Четыре справочника обновляются независимо,
а не в общей транзакции DAG. Блокировка PostgreSQL сериализует обновления одного
справочника. Повторная успешная загрузка того же файла не создаёт дубликатов.

Комментарии страны и заголовок часовых поясов пропускаются. Пустые поля сохраняются
в staging, а в core преобразуются в NULL. Обратные слеши и кавычки в значениях
не интерпретируются как управляющие символы COPY. Скачивание ограничено 10 МиБ
на файл, используются блоки 64 КиБ и сетевые таймауты. Временные файлы удаляются
при завершении задачи, в том числе при обычной ошибке; аварийное завершение
процесса может оставить файлы. XCom содержит только число загруженных строк.

Подключение `geonames_dwh` разрешается через Task SDK только во время выполнения
задачи. Импорт файла DAG не обращается к сети или БД.

Проверки парсера на собранном образе из PowerShell:

```powershell
docker run --rm --memory 512m --cpus 1 --mount "type=bind,source=$((Get-Location).Path)/tests,target=/checks,readonly" --entrypoint python geonames-airflow:dev -m unittest discover -s /checks -v
```

Проверка импорта для Airflow 3.4:

```powershell
docker run --rm --memory 512m --cpus 1 --entrypoint python geonames-airflow:dev -c "from airflow.dag_processing.dagbag import DagBag; b = DagBag('/opt/airflow/dags'); assert not b.import_errors, b.import_errors; assert 'geonames_references' in b.dags; print(b.dags['geonames_references'].task_ids)"
```

После успешных проверок пересоберите и обновите компоненты Airflow с учётом
доступной памяти (по одному, как описано в разделе ресурсов), затем включите
DAG и запустите его в UI. При первом включении возможен запуск по расписанию:
перед ручным запуском проверьте, что уже нет активного запуска. После выполнения
проверьте количество строк в четырёх таблицах core.

Проверка 17.11.2026 с лимитом WSL 4 ГБ и без triggerer: DAG выполнился по
расписанию, затем успешно выполнен повторный ручной запуск. После обоих запусков
получены одинаковые количества строк: country — 252, admin1 — 3865,
feature_code — 685, timezone — 418. Временные каталоги справочников удалены,
семь сервисов имеют статус healthy. На снятых замерах контейнеры потребляли
около 1,36–1,48 ГиБ суммарно (не измерение пикового расхода), в Windows после
первой загрузки оставалось около 7,4 ГиБ свободной памяти. Эти результаты
относятся к небольшим справочникам, а не к allCountries.zip.

На новой БД SQL выполняется автоматически. Для уже созданного тома примените
файл явно (значения `-U` и `-d` должны соответствовать вашему `.env`):

```powershell
Get-Content -Raw -Encoding UTF8 sql/init/002-reference-tables.sql | docker compose exec -T postgres-dwh psql -v ON_ERROR_STOP=1 -U geonames -d geonames
```

Создание выполняется в транзакции, повторный запуск сохраняет существующие
таблицы и данные. `IF NOT EXISTS` не изменяет структуру уже существующей таблицы:
для последующих изменений потребуются отдельные миграции.
